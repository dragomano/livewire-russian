# Токены выпуска

Токены выпуска (release tokens) делают устаревшими страницы, которые уже открыты в браузерах пользователей, когда деплой делает состояние их компонентов несовместимым с новым кодом.

## Зачем нужны токены выпуска

Livewire хранит состояние компонента в [снимке](/advanced/hydration#снимок), который живёт в браузере. Вкладка, открытая до деплоя, всё ещё хранит снимок, созданный старым кодом, и при следующем взаимодействии отправляет этот снимок новому коду.

Большинство деплоев обходятся без всякой помощи. Новая разметка, новые методы и изменения внутри существующих методов вступают в силу уже на следующем запросе, потому что ответ отрисовывает новый код.

С изменениями публичных свойств компонента всё иначе. Возьмём компонент `todos`, у которого появилось свойство, заполняемое в `mount()`:

```php hl_lines="8 12" title="resources/views/components/⚡todos.blade.php"
<?php

use Livewire\Component;

new class extends Component {
    public string $search = '';

    public array $filters;

    public function mount()
    {
        $this->filters = ['status' => 'open'];
    }
};
```

`mount()` выполняется только при первой отрисовке компонента, поэтому страница, открытая до деплоя, так и не запустит `mount()`. На её следующем запросе `$filters` будет пустым массивом вместо `['status' => 'open']`, и Livewire не выбросит ни одной ошибки.

Токены выпуска решают эту проблему: они помечают каждый снимок значением, которым управляете вы. Когда значение в снимке перестаёт соответствовать коду, Livewire отклоняет запрос и предлагает пользователю обновить страницу вместо того, чтобы запускать новый код со старым состоянием.

## Когда менять токен

В таблице ниже показано, что происходит на следующем запросе страницы, открытой до деплоя, если токен не изменился:

| Изменение в деплое | Результат на старой странице |
|---|---|
| Добавлено публичное свойство, заполняемое в `mount()` | Никогда не получает значение из `mount()`, обычно без всякой ошибки |
| Удалено или переименовано публичное свойство | Теряет старое значение без всякой ошибки. Переименованное свойство начинает с пустого значения |
| Изменён смысл значения свойства (например, с долларов на центы) | Воспринимает старое значение в новом формате без всякой ошибки |
| Изменён тип свойства | Выбрасывает `TypeError`, если старое значение не подходит по типу |
| Удалён или переименован публичный метод | Выбрасывает `MethodNotFoundException`, если страница вызывает этот метод |
| Удалён или переименован компонент | Автоматически показывает диалог устаревшей страницы |

Первые три строки — как раз те, за которыми стоит следить, поскольку ничто не сообщает о том, что компонент работает с некорректным состоянием. Меняйте токен, когда деплой вносит одно из этих изменений, а затронутая страница всё ещё может быть открыта.

!!! info "Продакшен и режим отладки ведут себя по-разному"
    С выключенным `APP_DEBUG` исключения `TypeError` и `MethodNotFoundException`, о которых шла речь выше, возвращают 419, поэтому пользователи видят тот же диалог устаревшей страницы. С включённым — полную страницу с ошибкой.

## Как комбинируются токены

Каждый снимок хранит свой токен выпуска в `memo.release`. Значение объединяет три отдельных токена, каждый из которых по умолчанию равен `a`:

```json
{
    "memo": {
        "name": "todos",
        "release": "a-a-a"
    }
}
```

В указанном порядке это токены:

| Токен | Задаётся | Что устаревает |
|---|---|---|
| Livewire | Самим Livewire | Все компоненты, когда выпуск Livewire делает существующие снимки несовместимыми |
| Приложение | `release_token` в `config/livewire.php` | Все компоненты приложения |
| Компонент | Методом `releaseToken()` компонента | Только этот компонент |

При каждом последующем запросе Livewire формирует это значение из текущего кода и сравнивает его со значением из снимка. Любое различие — это несовпадение. Других значений у этих токенов нет, поэтому подойдёт любая строка.

## Устаревание всех компонентов

Значение `release_token` из конфигурации делает устаревшими все открытые страницы, когда оно меняется. Если файл конфигурации ещё не опубликован, сначала опубликуйте его:

```shell
php artisan livewire:config
```

Затем измените значение:

```php
'release_token' => 'b',
```

Приложениям, которые кэшируют конфигурацию, нужно выполнить `php artisan config:cache`, чтобы новое значение вступило в силу.

### Устаревание при каждом деплое

Токен также можно получать из окружения — тогда скрипт деплоя сможет задавать его, например, равным текущему коммиту:

```php
'release_token' => env('LIVEWIRE_RELEASE_TOKEN', 'a'),
```

Такой подход избавляет от необходимости что-то запоминать, но при этом прерывается каждая открытая вкладка при каждом деплое, включая деплои, которые не затрагивали ни один компонент. Для большинства приложений выгоднее менять токен вручную только тогда, когда это действительно нужно.

!!! warning "Токен должен оставаться стабильным"
    Не используйте значение, которое меняется между запросами или серверами, например `time()`, `Str::random()` или имя хоста. Снимок, созданный в одном запросе, окажется недействительным в следующем, и каждое взаимодействие будет показывать диалог устаревшей страницы. То же самое ненадолго происходит во время скользящего деплоя, если страница, отрисованная новым сервером, отправит свой следующий запрос старому.

## Устаревание одного компонента

Если изменение затрагивает только один компонент, переопределите статический метод `releaseToken()` в этом компоненте, чтобы не прерывать остальное приложение:

```php hl_lines="8-11" title="resources/views/components/⚡todos.blade.php"
<?php

use Livewire\Component;

new class extends Component {
    public array $filters;

    public static function releaseToken(): string
    {
        return 'b';
    }

    public function mount()
    {
        $this->filters = ['status' => 'open'];
    }
};
```

Livewire объединяет компоненты, обновляющиеся одновременно, в один запрос, и устаревший компонент делает неуспешным весь этот запрос, включая актуальные компоненты, которые были в нём. Такие компоненты работают нормально в собственных запросах.

## Что видят пользователи

При несовпадении выбрасывается `LivewireReleaseTokenMismatchException`, которая возвращает ответ 419. В браузере Livewire затем показывает диалог:

```
This page has expired.
Would you like to refresh the page?
```

Действие, спровоцировавшее запрос, не выполняется. Если пользователь соглашается, страница перезагружается со свежим снимком, и всё, что он успел напечатать, но не сохранить, теряется.

Если он отказывается, страница остаётся как есть. Диалог больше не появляется, поэтому устаревшие компоненты молча перестают работать до перезагрузки страницы. `wire:poll` также останавливается для всех компонентов на странице.

Livewire не считает несовпадение ни ошибкой, ни попыткой подмены данных:

* Laravel не сообщает об этом исключении в логи или систему отслеживания ошибок
* Livewire проверяет токен раньше, чем [контрольную сумму снимка](/advanced/security#контрольные-суммы-снимков), поэтому устаревший снимок никогда не приводит к `CorruptComponentPayloadException`
* Несовпадение не учитывается в лимите на количество неудачных проверок контрольной суммы

## Как настроить диалог устаревшей страницы

Чтобы заменить диалог, добавьте [перехватчик запросов](/advanced/javascript#перехватчики-запросов) в свой макет и вызывайте `preventDefault()` для ответов с кодом 419:

```html
<script>
    document.addEventListener('livewire:init', () => {
        let notified = false

        Livewire.interceptRequest(({ onError }) => {
            onError(({ response, preventDefault }) => {
                if (response.status !== 419) return

                preventDefault()

                if (notified) return

                notified = true

                showRefreshBanner()
            })
        })
    })
</script>
```

Вызов `preventDefault()` также отключает поведение, описанное выше, поэтому в этом примере флаг `notified` отслеживается вручную. `wire:poll` продолжает отправлять запросы, а обработчик запускается для каждого неуспешного запроса.

Код 419 не всегда означает несовпадение токена выпуска. Истёкший CSRF-токен возвращает тот же статус, как и производственные сбои, описанные в разделе [Когда менять токен](#когда-менять-токен), поэтому любое собственное сообщение должно охватывать страницу, устаревшую по любой причине.
